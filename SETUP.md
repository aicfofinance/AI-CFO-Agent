# SETUP.md

## AI CFO Agent — Environment and Database Setup

This document covers the manual setup steps that are **not** performed automatically by
`pnpm install`, `pnpm db:generate`, or `pnpm db:migrate`. The most important of these is the
**manual Row Level Security (RLS) migration**, which is a deliberate manual step and must never
be automated into the Drizzle migration flow.

---

## 1. Prerequisites

- Node.js (see `.nvmrc`)
- `pnpm` (see `packageManager` in `package.json`)
- A Supabase project (free tier is sufficient for development)

Copy `.env.example` to `.env.local` and fill in every required variable. Environment variables
are validated at build time by `src/lib/env.ts` — a missing required variable fails the build.

---

## 2. Database schema migrations (Drizzle)

The Drizzle schema lives in `src/lib/platform/db/schema.ts`. Migrations are generated and applied
with:

```bash
pnpm db:generate   # generates a new SQL migration in src/lib/platform/db/migrations/
pnpm db:migrate    # applies pending migrations to the database
```

- Migration files under `src/lib/platform/db/migrations/` are generated by `drizzle-kit`. **Never
  hand-edit them.**
- Migrations use the **direct** connection (`dbDirect`, port 5432), not the pooler.

---

## 3. Manual RLS migration (CRITICAL — apply by hand)

Row Level Security policies are defined in:

```
src/lib/platform/db/rls-policies.sql
```

**This file is applied MANUALLY via the Supabase SQL Editor. It is never run by Drizzle and is not
part of the `pnpm db:migrate` flow.**

RLS is our defense-in-depth layer for multi-tenant isolation: every org-scoped table also enforces
`org_id` filtering at the application layer, but RLS ensures that a misconfigured or forgotten
application-layer filter cannot leak one organization's financial data to another.

### How to apply the RLS policies

1. Run the Drizzle migrations first (`pnpm db:migrate`) so every table the policies reference
   already exists.
2. Open the **Supabase Dashboard → SQL Editor** for your project.
3. Open `src/lib/platform/db/rls-policies.sql`, copy its entire contents, and paste it into a new
   SQL Editor query.
4. Run the query. It enables RLS on every org-scoped table and creates the isolation policies.
5. Verify isolation: query an org-scoped table (e.g. `findings`) as a user in Org A filtering by
   Org B's `org_id` and confirm it returns 0 rows.

### Rules for `rls-policies.sql`

- Re-apply this file **manually** whenever it changes. It will not be picked up by a Drizzle
  migration.
- Do not move RLS statements into a Drizzle migration file. Keeping RLS as an explicit, reviewed
  manual step is intentional — it forces a human to confirm the security posture on every change.
- Treat this file as a security-critical, no-touch-adjacent zone: do not modify it unless a task
  explicitly requires an RLS change.

## 4. Background jobs (Inngest)

Inngest function definitions live in `jobs/` (not `src/`). They are registered in the single serve
handler at `src/app/api/webhooks/inngest/route.ts`.

- `jobs/alerts/evaluate.ts` is a **V1 remnant** and must never be registered in the Inngest serve
  handler. Alert/anomaly detection was absorbed into `jobs/intelligence/run.ts` in V2.
