# AGENTS.md
## AI CFO Agent — Subagent Architecture

This file governs task routing in the 4-agent Claude Code subagent setup. Read it before assigning any task. Every agent must read **CLAUDE.md** before writing a single line of code — the behavioral rules and never-do list there apply to all agents equally.

> **Stack correction:** The prompt template for this project refers to "Prisma schema." This project uses **Drizzle ORM**, not Prisma. The canonical schema file is `src/lib/platform/db/schema.ts`, not `prisma/schema.prisma`. All references to "Prisma" in task descriptions should be understood to mean `src/lib/platform/db/schema.ts` and the `pnpm db:generate` / `pnpm db:migrate` workflow.

## 3. Shared Files — High Collision Risk

These files are read by multiple agents. Only the owning agent writes to them directly. Other agents must go through the orchestrator to request changes.

---

### `src/types/financial.ts` — owned by `backend-engineer`

This is the canonical domain type file. It exports the `Transaction`, `Account`, `FinancialSnapshot`, `Category`, and related types that every layer of the product uses.

**Who reads it:** all four agents.

**Who writes it:** backend-engineer only.

**How other agents propose additions:**
- integration-engineer: if a new QB/Xero field is being imported and needs a new type, describe it in the task handoff note (see Section 4). The orchestrator assigns the type addition to backend-engineer as a prerequisite step before integration-engineer's import task can proceed.
- ai-engine-engineer: if the intelligence engine produces a new finding shape, describe it in a type proposal comment. backend-engineer merges the type into `financial.ts` before ai-engine-engineer stores findings.
- product-engineer: if a component needs a prop type derived from a financial entity, use the existing types in `financial.ts` and compose locally within the component file. Do not modify `financial.ts` for UI-local types.

---

### `src/types/api.ts` — owned by `backend-engineer`

Exports `ApiResponse<T>`, `ApiError`, `PaginatedResponse<T>`, and all API request/response shapes for the endpoints backend-engineer owns.

**Who reads it:** all four agents.

**Who writes it:** backend-engineer only.

**Protocol:** When backend-engineer creates a new API endpoint, it adds the response type to `api.ts` in the same commit as the endpoint. product-engineer and ai-engine-engineer import from `api.ts` — they never define their own response types for existing endpoints.

---

### `src/lib/platform/db/schema.ts` — owned by `backend-engineer`

The Drizzle ORM table definitions for all 21 org-scoped tables. This is the equivalent of `prisma/schema.prisma` in projects that use Prisma.

**Who reads it:** all four agents must understand it to write correct queries.

**Who writes it:** backend-engineer only — no exceptions.

**How other agents request schema changes:** File a schema change request with the orchestrator. Include:
1. The table name
2. The column name, Drizzle type, nullable/default
3. The reason (what feature needs it)
4. Which step in IMPLEMENTATION_PLAN.md requires it

The orchestrator assigns the change to backend-engineer, who:
1. Modifies `schema.ts`
2. Runs `pnpm db:generate` (generates migration file in `migrations/`)
3. Runs `pnpm db:migrate` (applies to dev database)
4. Commits both `schema.ts` and the generated migration file atomically
5. Notifies the requesting agent that the column is available

The requesting agent may not proceed with any code that depends on the new column until this four-step process is complete and committed.

---

### `src/lib/ai/models/router.ts` — owned by `ai-engine-engineer`

The sole file in the codebase that imports `anthropic` from `@ai-sdk/anthropic` or `google` from `@ai-sdk/google`. Exports `getModel(complexityScore?)` and `detectRateLimitError(error)`.

**Who reads it:** all agents that need to understand AI routing.

**Who writes it:** ai-engine-engineer only.

**Who may call it:** all agents — but specifically ai-engine-engineer calls it from `jobs/intelligence/run.ts` and `src/lib/ai/streaming/handler.ts`. backend-engineer calls it from report generation in `jobs/reports/monthly.ts`. Any agent that needs to call an AI model imports `getModel()` from this file — it never imports the provider directly.

---

### `package.json` — owned by `backend-engineer`

**Who adds dependencies:** Any agent may require a new package. The protocol is:
1. The requesting agent states the package name, version, and reason in the task description.
2. The orchestrator confirms the addition is consistent with the tech stack documented in TECH_STACK.md.
3. backend-engineer runs `pnpm add package@version` and commits `package.json` + `pnpm-lock.yaml`.
4. Other agents must not run `pnpm add` independently — lockfile conflicts in a monorepo-style project are painful to resolve and easy to avoid.

**Prohibited packages:** Any direct import of `@prisma/client`, `mongoose`, `typeorm`, or other ORM packages — this project uses Drizzle exclusively. Any email provider SDK other than `resend`. Any additional AI SDK beyond `ai`, `@ai-sdk/anthropic`, `@ai-sdk/google`, `@anthropic-ai/sdk`.

---

### `src/app/api/webhooks/inngest/route.ts` — owned by `backend-engineer`

The Inngest serve handler that registers all background job functions from all agents. Every agent that creates a new Inngest function must have it registered here.

**Registration protocol:** When an agent creates a new Inngest function (e.g., ai-engine-engineer adds `intelligenceFanOut` in `jobs/intelligence/run.ts`), the agent notifies the orchestrator. backend-engineer adds the import and registration in the same commit that the new function is finalized. No agent self-registers their functions — backend-engineer is the gatekeeper.

---

### `src/lib/env.ts` — owned by `backend-engineer`

The T3 env validation schema. Every environment variable used anywhere in the codebase is defined here.

**Protocol:** When an agent needs a new env variable (e.g., integration-engineer adds a new QB credential):
1. Agent describes the variable name, type (`z.string().min(1)`, `z.enum([...])`, etc.), and when it becomes required.
2. backend-engineer adds it to `src/lib/env.ts` as `.optional()` initially.
3. backend-engineer updates `.env.example` with the variable name and a dummy value.
4. When the variable is required at runtime, backend-engineer promotes it to a required validator.

No agent writes `process.env.VARIABLE_NAME` anywhere. All access goes through the `env` export from `src/lib/env.ts`.

## 4. Integration Handoff Protocol

---

### When `integration-engineer` completes a new data sync

**What must be committed before handoff:**

1. **Normalize output is typed.** Every `normalize.ts` file must export a function whose return type is explicitly `NormalizedTransaction` from `src/types/financial.ts`. No `any`, no inferred return types. If the normalized shape requires a new field that doesn't exist in `NormalizedTransaction`, file a type addition request (see Section 3) before the normalization is considered complete.

2. **The QB/Xero field mapping is documented.** Each `normalize.ts` file includes a comment block listing:
   - The source field name from the QB/Xero API
   - The internal column it maps to in the `transactions` table
   - The handling for null/missing values
   - Any fields that are intentionally dropped

3. **Unmapped categories are logged, not silently discarded.** Any transaction whose QB/Xero category does not map to the 15-category internal schema must be logged to `data_quality_log` with the original category string and marked as `'other'`. This is observable evidence that the category mapping needs updating.

4. **The sync job step ordering is preserved.** `single-org.ts` must maintain the three-step order: `pull-transactions` → `recompute-snapshots` → `trigger-intelligence-run`. The `recompute-snapshots` step runs financial_snapshots computation via backend-engineer's `recomputeSnapshots()` function. integration-engineer must call this function — it may not skip it or inline an alternative.

**What backend-engineer must know before writing queries against synced data:**

- Which `source_system` value the new integration uses (`'quickbooks'`, `'xero'`, `'csv'`)
- Whether all expected transaction types produce rows in all four expected categories: `income`, `expense`, `transfer`, `other`
- Whether the integration populates `amount_base` (base currency) for multi-currency orgs
- Whether `external_id` is globally unique per org (required for deduplication) or only unique per `source_system`

---

### When `backend-engineer` creates a new API endpoint

**What must be committed before handoff to `product-engineer`:**

1. **The response type is exported from `src/types/api.ts`.** The type is named after the endpoint's resource: `FinancialSummaryResponse`, `FindingFeedResponse`, `ConnectionListResponse`. product-engineer imports this type and uses it for its `fetch()` call return type.

2. **The endpoint is documented with its exact URL, method, auth requirement, query params, request body shape, and all error codes.** A single-file doc comment in the route file is acceptable for simple endpoints. Complex endpoints with multiple response states require a section in BACKEND_STRUCTURE.md.

3. **The `ApiResponse<T>` envelope is used.** Success responses are `{ data: ResponseType }`. Error responses are `{ error: { code, message, request_id } }`. product-engineer can write a typed `fetchApi<T>` wrapper that expects this shape — it should never have to handle raw objects.

4. **Auth requirements are explicit.** The route file's first comment or JSDoc states: "Requires session + [role if applicable]. Returns 401 if unauthenticated, 403 if insufficient role."

**What `ai-engine-engineer` must know before using a new financial data endpoint:**

- The exact fields available in the response (especially DECIMAL-as-string fields for monetary values)
- The maximum response size (relevant for context window budget)
- Whether the endpoint uses the `financial_snapshots` fast path or performs live aggregation (matters for intelligence engine timing)

---

### When `ai-engine-engineer` creates a new financial prompt or context builder

**What must be committed before handoff to `product-engineer`:**

1. **The streaming handler exports a typed function signature.** If a new conversation type is being added (e.g., a "deep dive" analysis mode), the function signature is exported from `src/lib/ai/streaming/handler.ts` with typed parameters. product-engineer calls this via the API route — it never calls AI functions directly.

2. **The API endpoint is the interface, not the prompt.** product-engineer calls `POST /api/conversations/:id/messages` — it never imports from `src/lib/ai/`. If a new capability (e.g., "analyze this report") requires a new API route, ai-engine-engineer files the route creation with the orchestrator → backend-engineer creates the route → product-engineer consumes it.

3. **The disclaimer is verified before handoff.** Any new AI response surface must append the standard disclaimer as the final text chunk via `src/lib/ai/streaming/handler.ts`. ai-engine-engineer must confirm this in the task completion note: "Disclaimer injection verified — final chunk is the standard financial disclaimer."

4. **New finding types are registered.** If the intelligence engine adds a new `finding_type` value (beyond the five defined in BACKEND_STRUCTURE.md), it must:
   - Add the value to the `finding_type` enum check in `schema.ts` (request from backend-engineer)
   - Add the `hasActionableType: boolean` logic in `GET /api/intelligence/feed` to indicate whether the new type supports draft generation
   - Notify product-engineer of the new severity + icon mapping required in `FindingCard.tsx`

## 5. Conflict Rules

---

### Files that require a committed state before another agent may depend on them

These files may not be depended upon in an uncommitted state. If integration-engineer is mid-flight on `normalize.ts` and ai-engine-engineer tries to run the intelligence engine, it will fail against the uncommitted normalization logic. Coordinate through the orchestrator.

| File | Rule |
|---|---|
| `src/lib/platform/db/schema.ts` | backend-engineer must commit schema change + migration before any agent writes code that depends on the new column. |
| `src/lib/platform/db/migrations/*` | Migration files are generated by `pnpm db:generate` and committed atomically with `schema.ts`. Never edit migration files by hand. |
| `src/types/financial.ts` | backend-engineer must commit type changes before any agent imports the new type. |
| `src/types/api.ts` | backend-engineer must commit response type before product-engineer imports it. |
| `src/lib/ai/models/router.ts` | ai-engine-engineer must commit router changes before any agent calls `getModel()`. |
| `src/lib/platform/db/rls-policies.sql` | backend-engineer must apply and commit the RLS SQL via Supabase SQL Editor before any security test can pass. Manual step — not a migration file. |
| `src/app/api/webhooks/inngest/route.ts` | backend-engineer must commit new function registration before any agent can test the new Inngest function end-to-end. |

---

### Protocol: `integration-engineer` needs a new column in the `transactions` table

This is the most common cross-agent schema dependency. The exact steps:

1. **integration-engineer** files a schema change request with the orchestrator. The request must include:
   - Column name (snake_case)
   - Drizzle type (`decimal('col', { precision: 15, scale: 2 })`, `varchar('col', { length: 100 })`, etc.)
   - Nullable or not, and the default value if not null
   - The QB/Xero field that will populate it
   - The IMPLEMENTATION_PLAN step number requiring it

2. **Orchestrator** assigns a blocking task to **backend-engineer**: "Add column `[name]` to `transactions` table in `schema.ts`. Generate and apply migration. Commit both files."

3. **backend-engineer**:
   - Modifies `schema.ts` (the only person who may)
   - Runs `pnpm db:generate` (generates a new file in `src/lib/platform/db/migrations/`)
   - Runs `pnpm db:migrate` against the development database
   - Commits: `git add src/lib/platform/db/schema.ts src/lib/platform/db/migrations/ && git commit -m "schema: add [column] to transactions"`

4. **Orchestrator** unblocks **integration-engineer**'s task and provides the commit SHA.

5. **integration-engineer** pulls the commit, verifies the column exists in Drizzle Studio (`pnpm db:studio`), then proceeds with the import and normalization work.

**What integration-engineer must NOT do:** modify `schema.ts` directly, run `pnpm db:generate` themselves, or write import code that references a column before step 3 is complete. Any of these creates a divergent migration history that is expensive to resolve.

---

### Protocol: two agents need changes to the same API route file

This situation most commonly occurs at `src/app/api/connections/[id]/sync/route.ts` (integration-engineer owns the sync trigger; backend-engineer owns the connection CRUD) and `src/app/api/conversations/[id]/messages/route.ts` (ai-engine-engineer owns the streaming endpoint; backend-engineer owns the conversation CRUD parent).

**Rule:** The file's owning agent (as listed in Section 2) has final write authority. The non-owning agent proposes a change through the orchestrator. The owning agent reviews and merges it. Neither agent may commit a change to the other's file without the owning agent reviewing it first.

---

### Protocol: CI fails after a multi-agent task

If the CI pipeline fails (`pnpm tsc --noEmit`, `pnpm lint`, or `pnpm vitest run`) after a task that involved multiple agents:

1. The orchestrator assigns the failing check to the agent that owns the files the error occurs in (per Section 2).
2. That agent fixes the error in isolation — it does not modify files owned by other agents to make the error go away.
3. If fixing the error requires a change in another agent's file (e.g., a type mismatch between `src/types/financial.ts` and `src/lib/integrations/quickbooks/normalize.ts`), the orchestrator assigns the type fix to backend-engineer and the integration fix to integration-engineer as two sequential tasks.
4. The CI pipeline is the arbiter of completion — a task is not done until all four CI jobs (`typecheck`, `lint`, `test`, `build`) pass.
